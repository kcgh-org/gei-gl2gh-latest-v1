# GitLab to GitHub Migration using GL2GH

## Overview

This package provides scripts and a GitHub Actions workflow to migrate repositories from GitLab to GitHub using the GitHub-supported `gh-gl2gh` extension.

The migration uses GitHub extension `gl2gh` and focuses on three main stages:
1. Migration Readiness Check
2. Repository Migration
3. Post-Migration Validation

Supported targets:
- GitHub Enterprise Cloud
- GitHub Enterprise Cloud with Data Residency

---

## Migration Execution Options

### 1. Script-Based Execution
Use this option when running the migration scripts directly from a machine or VM.
Main scripts:
```text
1_migration_readiness_check.sh
2_migration.sh
3_post_migration_validation.sh
```
PowerShell equivalents may also be used if included in the package.

### 2. GitHub Actions Workflow Execution
Use this option to run the migration through the GitHub Actions workflow.
The workflow handles:
- Environment validation
- Prerequisite validation
- Migration readiness check
- Approval gate
- Repository migration
- Post-migration validation
- Artifact upload
- GitHub Actions job summaries

---

## Pipeline Flow
```text
Environment Validation
      ↓
Migration Readiness Check (Optional)
      ↓
Approval Stage (Only when readiness is enabled)
      ↓
Repository Migration
      ↓
Post-Migration Validation
```

Notes:
- Readiness can be run or skipped in runtime.
- When migration is selected in runtime, both repository migration and post-migration validation will run
- Post-migration validation uses `output_files/migration/repos_with_status.csv` generated by the migration stage.

## Required Access and Tokens

### GitLab Personal Access Token

The GitLab token is used to:

- Generate inventory
- Validate project access
- Check open merge requests
- Check running or pending pipelines
- Read branch and commit information for validation

Recommended scopes:

```text
read_api
api
```
### GitHub Personal Access Token

The GitHub token is used to:

- Authenticate GitHub CLI
- Run repository migrations
- Validate migrated repositories
- Access target organizations

Recommended scopes:

```text
repo
admin:org
workflow
user
```

If the user running migration is not a GitHub organization owner, a GitHub organization owner must grant the migrator role.

gh extension install https://github.com/github/gh-gl2gh

### gh-ado2gh

Used for migrator role assignment and mannequin reclamation.

## Inventory Preparation

### Generate Inventory

Generate the inventory using `gh gl2gh inventory-report`.

Example for all accessible projects:

```bash
gh gl2gh inventory-report \
  --gitlab-server-url https://gitlab.com \
  --gitlab-pat <GITLAB_PAT>
```

Example for a specific GitLab group:

```bash
gh gl2gh inventory-report \
  --gitlab-server-url https://gitlab.com \
  --gitlab-pat <GITLAB_PAT> \
  --gitlab-group <GITLAB_GROUP>
```

This generates inventory files such as:

```text
groups.csv
projects.csv
```

### Update projects.csv

Before migration, update `projects.csv` with the following required columns:

| Column | Description |
|---|---|
| `github_org` | Target GitHub organization |
| `github_repo` | Target GitHub repository name |
| `gh_repo_visibility` | Repository visibility: `public`, `private`, or `internal` |

The workflow and scripts use `projects.csv` by default unless another file name is provided.

## Script-Based Migration

### 1. Set Environment Variables

#### GitHub Enterprise Cloud

```bash
export GITLAB_SERVER_URL="https://gitlab.com"
export GITLAB_PAT="<gitlab-pat>"
export GH_PAT="<github-pat>"
export GITHUB_API_URL="https://api.github.com"
export INVENTORY_FILE="projects.csv"
export STORAGE_TYPE="GITHUB"
```

#### GitHub Enterprise Cloud with Data Residency

```bash
export GITLAB_SERVER_URL="https://gitlab.com"
export GITLAB_PAT="<gitlab-pat>"
export GH_PAT="<github-pat>"
export GITHUB_API_URL="https://api.SUBDOMAIN.ghe.com"
export TARGET_UPLOAD_URL="https://uploads.SUBDOMAIN.ghe.com"
export INVENTORY_FILE="projects.csv"
export STORAGE_TYPE="GITHUB"
```

#### Azure Storage

```bash
export STORAGE_TYPE="AZURE"
export AZURE_STORAGE_CONNECTION_STRING="<azure-storage-connection-string>"
```

#### AWS Storage

```bash
export STORAGE_TYPE="AWS"
export AWS_BUCKET_NAME="<aws-bucket-name>"
export AWS_REGION="<aws-region>"
export AWS_ACCESS_KEY_ID="<aws-access-key>"
export AWS_SECRET_ACCESS_KEY="<aws-secret-key>"
```

---

### 2. Run Migration Readiness Check

```bash
sh 1_migration_readiness_check.sh
```

The readiness check validates:

- Open GitLab merge requests
- Running GitLab pipelines
- Pending GitLab pipelines
- GitLab project access

Output is written under:

```text
logs/1_migration_readiness_check/
```

---

### 3. Run Repository Migration

```bash
sh 2_migration.sh
```

The migration script:

- Reads repositories from `projects.csv`
- Runs GitLab-to-GitHub migration using `gh gl2gh migrate-repo`
- Supports parallel execution
- Generates migration logs
- Generates repository status output

Key output:

```text
output_files/migration/repos_with_status.csv
```

---

### 4. Run Post-Migration Validation

```bash
sh 3_post_migration_validation.sh
```

The validation script reads:

```text
output_files/migration/repos_with_status.csv
```

Validation checks include:

- GitHub repository existence
- Branch count comparison
- Branch name comparison
- Default branch comparison
- Commit count validation
- Latest SHA validation

If a repository has more than the configured branch validation threshold, the script validates the default branch and a limited set of additional branches.

Generated outputs:

```text
output_files/post_migration_validation/validation-summary_<timestamp>.csv
output_files/post_migration_validation/validation-summary_<timestamp>.md
```

## GitHub Actions Workflow Execution

### GitHub Environment Setup

Create a GitHub Environment to store migration secrets and variables.

Example environment name:

```text
gl2gh-migration-secrets
```

Required secrets:

| Secret | Description |
|---|---|
| `GITLAB_PAT` | GitLab Personal Access Token |
| `GH_PAT` | GitHub Personal Access Token |
| `AZURE_STORAGE_CONNECTION_STRING` | Required only when using Azure Storage |
| `AWS_ACCESS_KEY_ID` | Required only when using AWS Storage |
| `AWS_SECRET_ACCESS_KEY` | Required only when using AWS Storage |
| `AWS_SESSION_TOKEN` | Optional, used when required by AWS authentication |

Required or optional variables:

| Variable | Description |
|---|---|
| `GITLAB_SERVER_URL` | GitLab server URL. Defaults to `https://gitlab.com` if not configured |
| `STORAGE_TYPE` | `GITHUB`, `AZURE`, or `AWS`. Defaults to `GITHUB` |
| `TARGET_UPLOAD_URL` | Required for GitHub Enterprise Cloud with Data Residency when using GitHub storage |
| `AWS_BUCKET_NAME` | Required when using AWS storage |
| `AWS_REGION` | Required when using AWS storage |

---

### Approval Environment

Create a separate GitHub Environment for approval.

Example:

```text
gl2gh-migration-approvers
```

Configure required reviewers in this environment.

The approval stage is used only when the readiness check is enabled.

## Workflow Inputs

| Input | Description |
|---|---|
| `TARGET_GITHUB_API_URL` | GitHub API URL. Use `https://api.github.com` for GitHub Enterprise Cloud or `https://api.SUBDOMAIN.ghe.com` for Data Residency |
| `ENVIRONMENT_NAME` | GitHub Environment containing migration secrets and variables |
| `INVENTORY_FILE` | Inventory CSV file name. Default: `projects.csv` |
| `APPROVAL_ENVIRONMENT_NAME` | GitHub Environment used for approval |
| `USE_SELF_HOSTED_RUNNER` | Set to `true` to use a self-hosted runner |
| `SELF_HOSTED_RUNNER_LABEL` | Runner label to use when self-hosted runner is enabled |
| `RUN_MIGRATION_READINESS` | Set to `true` to run readiness check and approval before migration |
| `RUN_MIGRATION` | Set to `true` to run migration and post-migration validation |

## GitHub Actions Runtime Behavior

### Runner Selection

If `USE_SELF_HOSTED_RUNNER=false`, the workflow uses:

```text
ubuntu-latest
```

If `USE_SELF_HOSTED_RUNNER=true`, the workflow uses the value provided in:

```text
SELF_HOSTED_RUNNER_LABEL
```

### Timeout Behavior

| Runner Type | Timeout |
|---|---|
| GitHub-hosted runner | 360 minutes |
| Self-hosted runner | 7200 minutes |

GitHub Actions does not support unlimited timeout. For self-hosted runners, the workflow uses the maximum practical timeout of five days.

## Mannequin Reclamation

If GitLab users are migrated as mannequins, generate and update the mannequin CSV after migration.

### GitHub Enterprise Cloud

```bash
gh ado2gh generate-mannequin-csv --github-org "<github-org>"
```

```bash
gh ado2gh reclaim-mannequin \
  --github-org "<github-org>" \
  --csv mannequins.csv \
  --skip-invitation
```

### GitHub Enterprise Cloud with Data Residency

```bash
gh ado2gh generate-mannequin-csv \
  --github-org "<github-org>" \
  --target-api-url https://api.SUBDOMAIN.ghe.com
```

```bash
gh ado2gh reclaim-mannequin \
  --github-org "<github-org>" \
  --csv mannequins.csv \
  --skip-invitation \
  --target-api-url https://api.SUBDOMAIN.ghe.com
```

## Troubleshooting

### Authentication Issues

Verify:

- GitLab token is valid
- GitHub token has required scopes
- GitHub token is SSO-authorized for the target organization
- GitHub CLI is authenticated to the correct host

```bash
gh auth status
```

For Data Residency:

```bash
gh auth status --hostname SUBDOMAIN.ghe.com
```

### Target Repository Already Exists

If migration fails because the target repository already exists:

- Use another target repository name
- Archive the existing repository
- Delete the existing repository only if approved

### Post-Migration Validation Failure

Check:

```text
output_files/migration/repos_with_status.csv
output_files/post_migration_validation/
logs/3_post_migration_validation/
```

Validation depends on repositories that migrated successfully.

### Cancel Migration

Use the migration ID if an active migration must be aborted.

```bash
gh ado2gh abort-migration --migration-id "<migration-id>"
```

For Data Residency:

```bash
gh ado2gh abort-migration \
  --migration-id "<migration-id>" \
  --target-api-url https://api.SUBDOMAIN.ghe.com
```

## Developer Verification Checklist

After migration, repository owners should verify:

- Repository is accessible in GitHub
- Branches are present
- Commit history is available
- Files and folders are present
- Default branch is correct
- Users can clone, pull, and push as expected
- Pull requests can be created
- Branch protection and repository permissions are correct
- Required workflows and integrations are updated

Example:

```bash
git clone https://github.com/<org>/<repo>.git
cd <repo>
git checkout -b test-migration-verification
echo "Migration test" >> test-file.txt
git add test-file.txt
git commit -m "Test commit post-migration"
git push origin test-migration-verification
```
